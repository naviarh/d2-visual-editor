# План: редактирование кода D2 с генерацией визуальной блок-схемы

Статус: черновик
Ветка: `feature/d2-parser`
Дата: 2026-08-06

---

## 1. Цель

Сделать код D2 полноценным вторым интерфейсом редактирования схемы:

- код D2 всегда видим слева и доступен для ручного редактирования;
- любая правка кода применяется к визуальной схеме (после debounce ~1 c);
- позиции существующих элементов **не теряются** ни при переименовании, ни при переносе строки, ни при вставке новых строк;
- новые элементы автоматически получают оптимальное позиционирование;
- кнопка «Показать/Скрыть позиции» переключает между чистым и аннотированным кодом;
- порядок блоков в коде устойчив (не «прыгает» после перегенерации) и по требованию упорядочивается по стрелкам.

## 2. Архитектура

**Граф — источник истины для хранения и структуры. D2-текст — проекция графа** (два сериализатора). Исключение — позиции при правке текста (правило приоритета ниже).

Почему не «аннотированный текст как источник»: тогда пришлось бы синхронно держать две текстовые копии и вживлять комментарии в отредактированный текст. При графе-источнике «комментарии не исчезают» означает «позиции не исчезают» — они живут в графе и заново сериализуются для каждого позиционированного элемента.

**Правило приоритета позиций** (снимает противоречие между «граф — источник» и «маркер на строке»):

1. Если в редактируемом тексте у элемента есть маркер `@d2pos` — маркер авторитетен (пользователь видит/правит числа в аннотированном виде).
2. Если маркера нет (чистый вид) — позиция переносится из текущего графа через merge-слой (id → эвристики).
3. Совсем новый элемент без маркера — авто-расстановка (раздел 6).

Это объясняет обе строки §5.2: переименование в аннотированном виде сохраняет позицию «бесплатно» (маркер уехал со строкой), в чистом виде — через эвристики.

Ключевое следствие: **сложная часть в любом случае одна** — сопоставление элементов отредактированного текста с существующими в графе (раздел 5). Формат хранения на неё не влияет.

## 3. Модель данных

### 3.1 Граф (в localStorage, ключ `d2editor:v2`)

```js
{
  v: 2,
  nodes: [ { id, label, x, y, w, h, parentId, children: [], rawAttrs: [],
             comments: [], trailingComment: null } ],
  edges: [ { id, source, target, label, comments: [], trailingComment: null } ],
  order: [ id, id, ... ],        // единственный порядок эмиссии: ноды и рёбра вперемешку, как в тексте
  headerComments: [],            // строки-комментарии до первого элемента
  trailingComments: [],          // строки-комментарии в конце файла
  idCounter: N,
  viewport: { x, y, zoom },
  showComments: true|false       // состояние кнопки «Показать/Скрыть»
}
```

- `id` — **локальный ключ сегмента** (последний сегмент пути), как в v1. Полный канонический ключ `a.b.c` строится цепочкой `parentId` (см. `nodePath` в сериализаторе). Именно полный ключ даёт стабильность матчинга в merge-слое. Ограничение (как в v1): локальные id не уникальны глобально — одинаковые имена в разных поддеревьях дают коллизию в `indexNodes` (редкий случай, задокументирован).
- **Ключ с точкой в кавычках** (`"b.c"`) — это литерал, а не путь: при разрешении пути сначала пробуется самый длинный совпадающий литеральный ключ, затем усечение по последней `.` (см. 4.2). Конфликт «литерал vs путь» редок и документирован в ограничениях.
- `children` — **только множество** (массив локальных id) для рендера и иерархии; его порядок на эмиссию не влияет — единственный источник порядка это `order` (снимает конфликт двух источников).
- `w/h` — размеры приходят из рендера/измерения; в тексте D2 их нет, поэтому круг-трип невозможен. Пользовательский размер в тексте сохраняется только через `rawAttrs`.
- `id` рёбер — служебный (для выделения/удаления, как в v1). Матчинг рёбер при merge — по тройке `(source, target, label)`, не по `id` (см. 5.1).
- `rawAttrs` — нераспознанные атрибуты блока (best effort, см. 8.2), сохраняются и перевыводятся, чтобы не терять код пользователя.
- `comments` — строки-комментарии пользователя (на отдельной строке, над элементом); `trailingComment` — текст инлайн-комментария в конце строки элемента (без маркера).
- Миграция с `v1`: у v1 нет `order` — он строится как `treeOrder()` (ноды) + рёбра в конец.

### 3.2 Позиционный маркер и комментарии пользователя

Позиционный маркер — `# @d2pos x,y`, всегда в **конце комментария строки элемента**, координаты **относительно родителя** (совпадают с `n.x/n.y`):

```
Client # @d2pos 60,300
"API Server": { # @d2pos 340,230
  Database # @d2pos 40,60
}
```

**Ключевое ограничение D2:** на строке может быть только один комментарий — от первого `#` до конца строки (проверено компилятором: `d2 a.d2 out.svg` принимает `a -> b # note # pos` целиком как один комментарий). Поэтому правило совмещения:

> Пользовательский комментарий, написанный в конце строки, сохраняется первым, а позиционный маркер **дописывается после него в тот же комментарий**:
> `Client # front-end сервис # @d2pos 60,300`

Отделение маркера от текста пользователя — регулярным выражением, якорем на конец строки:
`/#\s*@d2pos\s*(-?\d+),\s*(-?\d+)\s*$/`.
Всё, что до маркера внутри комментария, — текст пользователя. Если маркера нет — весь комментарий пользовательский.

- Контейнер: маркер на строке с открывающим `{`.
- Рёбра маркер **не получают** (они пересчитываются из боксов нод, см. `edgeGeometry`); инлайн-комментарий ребра сохраняется без маркера.
- Кодирование ключа/метки — существующий `d2Key` (кавычки). `#` внутри строковых литералов маркером не считается.
- `@d2pos` — зарезервированный маркер: пользовательский комментарий, заканчивающийся точно таким паттерном, будет распознан как позиционный (редкий случай, задокументирован в ограничениях).

## 4. Парсер D2 → граф (`parseD2`)

### 4.1 Обработка строк

- Один `#`-комментарий на строку (от первого `#` до конца строки, вне кавычек `"..."`) — поведение проверено компилятором d2.
- **Извлечение маркера**: по якорному regex `#\s*@d2pos\s*(-?\d+),(-?\d+)\s*$` из комментария строки. Маркер → позиция элемента; остаток комментария (непустой) → `trailingComment`.
- **Строки-комментарии** (отдельная строка с `#`, без маркера): в `comments[]` следующего элемента того же скоупа; до первого элемента — `headerComments`; в конце файла — `trailingComments`.
- Пропуск пустых строк.

### 4.2 Разбор

- **Скоупы**: `key: { ... }` — вложенный блок (контейнер). Внутри — вложенные элементы и/или атрибуты.
- **Ключи**: без кавычек или в кавычках; вложенный путь `a.b.c` разрешается как каскад вложенных ключей. **Ключ с точкой в кавычках** (`"b.c"`) — литерал: при разрешении пути сначала пробуется самый длинный совпадающий литеральный ключ (`"b.c"` целиком), затем усечение по последней `.` (`b` → ребёнок `c`). Приоритет у более длинного ключа (литерала).
- **Атрибуты**: `label: значение`, `shape: ...` и др. `label` парсится в поле ноды; остальные сохраняются в `rawAttrs` (строка + отступ) и перевыводятся при сериализации. Блочные атрибуты (`style: { ... }`) и массивы (`pad: [10, 20]`) сохраняются в `rawAttrs` как многострочная строка и перевыводятся с сохранением относительного отступа.
- **Директивы** (`@def`, `@import`, ...): не поддерживаются — ошибка с номером строки (не молча ронять).
- **Рёбра**: 
  - `a -> b`, `a.b -> c.d` (пути разрешаются в id);
  - цепочки `a -> b -> c`;
  - списки `a, b -> c, d` (декартово произведение);
  - опциональный блок `{label: ...}`.
- **Позиции**: из маркера `@d2pos` (локальные). Если маркера нет — `x=0,y=0` и пометка «нет позиции» (`hasPos: false`; позиция придёт через merge-слой или авто-расстановку).
- **Неявные ноды**: D2 допускает `a -> b` без объявления `b` блоком — парсер создаёт неявную ноду `b` (label = b, без позиции, пометка `implicit: true`). Последующее явное объявление блока с тем же ключом сливается по id с неявной нодой (позиция из явного, либо авто-позиция).
- **Порядок**: по ходу парсинга заполняется массив `order` в порядке появления в тексте — **и ноды, и рёбра вперемешку** (это единственный источник порядка эмиссии, см. 7).
- **Комментарии пользователя** (строки и инлайн) сохраняются как непрозрачный контент и перевыводятся при сериализации (см. 7).

### 4.3 Ошибки

- Возвращать `{ ok, graph?, error: { line, col, message } }`.
- При ошибке графическое состояние **не трогаем**, в статус-строке показываем «Ошибка D2: строка N — ...».

## 5. Слой идентичности (merge) — самая важная часть

Задача: сопоставить элементы распарсенного текста с элементами текущего графа, чтобы перенести позиции и порядок. Без этого переименование или перенос = «удаление и добавление».

### 5.1 Алгоритм (жадный, best effort)

1. **Точное совпадение по id** (`a.b.c`). Быстрый путь — 90% случаев. Позиция и порядок остаются.
2. **Остаток** — для «осиротевших» новых элементов ищем кандидата среди удалённых:
   - совпадение `label`;
   - совпадение родителя (`parentId`);
   - пересечение соседей по label (входящие/исходящие рёбра).
   Считаем score; **переносим позицию только при score ≥ порога**, иначе — новый элемент.
3. **По-настоящему новые** (нет кандидата) → авто-расстановка (раздел 6), id из ключа, дописываются в конец `order`.
4. **Удалённые** — нода и её рёбра удаляются.
5. **Порядок прохода — двухпроходный**: сначала ноды (шаги 1–4), затем рёбра (шаг 6). Иначе переименование ноды в тексте ломает матчинг её рёбер до их обработки (старые id уже не найти).
6. **Рёбра**: матчинг по тройке `(source, target, label)` уже по **новым** id (после слияния нод): создаём/обновляем/удаляем. Подпись менялась — считаем новой; инлайн-комментарий ребра переносится при совпадении тройки.
7. **Ссылки выделения**: после merge `selectedId`/`selectedEdgeId`, указывающие на отсутствующий или переименованный элемент, сбрасываются в `null` (как в текущем коде: rename обновляет ссылку, delete сбрасывает).

### 5.2 Простые случаи (без эвристик)

- **Чистое переименование на строке** — id меняется, но в аннотированном тексте комментарий физически на той же строке → парсер считывает позицию из комментария напрямую. Позиция сохраняется «бесплатно».
- **Простой перенос строки** — id тот же → матч по ключу, позиция из графа/комментария на месте.
- **Вставка нового блока** — нет id и кандидата → авто-позиция.

### 5.3 Сложный случай (move + rename)

Эвристики из 5.1.2 с fallback в авто-расстановку. Гарантий нет — это осознанный компромисс (см. раздел 10).

## 6. Авто-расстановка новых элементов (`placeNewNode`)

Жадная, без внешних layout-движков:

1. Если есть исходящий/входящий сосед — стартовая точка рядом с ним (смещение ~80px по диагонали).
2. Иначе если есть родитель-контейнер — внутри него, с отступами PAD/HEAD.
3. Иначе — центр текущего вьюпорта (`centerFlow()`).
4. Проверка пересечений с существующими боксами (`absPos` + `boxSize`); при наложении — спиральный/шахматный поиск ближайшей свободной точки.

## 7. Сериализаторы

- `serializeClean(graph)` — по массиву `order`: ноды и рёбра эмиттятся в порядке текста (нода с детьми — блоком рекурсивно; уже выведенные в поддереве дети на верхнем уровне пропускаются). Квотинг `d2Key`; `label:` только если label ≠ id; перевывод `rawAttrs`, строк `comments[]` и инлайн `trailingComment`. Маркер `@d2pos` в чистом виде **не выводится**.
- `serializeAnnotated(graph)` — то же + позиционный маркер в конце комментария строки каждого позиционированного элемента (локальные координаты): `[trailingComment] # @d2pos x,y`. Инлайн-комментарий пользователя остаётся на месте (не переносится на отдельную строку), маркер дописывается после него.
- **Паритет**: аннотированный = чистый + маркеры. Проверяется тестом (раздел 9): оба варианта компилируются `d2` в идентичную структуру.

## 8. Упорядочение блоков

### 8.1 Стабильный порядок

- Эмиссия всегда по массиву `order`. Правка текста не «перепрыгивает» элемент в другое место кода: порядок обновляется только из текста (парсер) или при явной команде сортировки.

### 8.2 Упорядочивание по стрелкам (`sortByArrows`, опциональная команда «Упорядочить по связям»)

DFS pre-order по скоупам (см. обсуждение):

```
посетить(n):
  если посещён → выход
  пометить; вывести n
  для каждой исходящей стрелки n (в порядке создания):
    цель — контейнер или блок внутри контейнера → в отложенный список
    иначе → посетить(цель)
порядок = []
для блоков без входящих стрелок (в текущем порядке): посетить(...)
затем: обработать отложенные контейнеры/вложенные цели (DFS внутри скоупа)
непосещённый остаток — дописать в конец
```

- Иерархически: сортируются прямые дети каждого контейнера по тем же правилам; дети физически остаются внутри `{}`.
- **Входящие стрелки считаются внутри текущего скоупа** (прямые дети контейнера / корни верхнего уровня), а не глобально — иначе рёбра между скоупами дают ложные «без входящих» и ломают детерминизм.
- Циклы — защита множеством посещённых; порядок «примерно топологический».
- Детерминированность — от порядка рёбер (порядок создания).

## 9. Интеграция в UI

1. `textarea#out` — снять `readonly`.
2. Кнопка «Показать/Скрыть позиции» — переключение между сериализаторами в textarea (граф не меняется); состояние в `showComments` (persist).
3. **Правка текста → debounce 1 c** → `parseD2` → `merge` → `setGraph` → `render()` + перегенерация текстов.
   - **Не переписывать textarea во время ввода**, чтобы не ломать каретку. Переписывать только когда merge реально изменил структуру (добавлен/удалён блок) и пользователь остановился; иначе — только обновлять визуальную схему и противоположный вид (чистый↔аннотированный держать актуальным при следующем переключении).
   - **Ошибка парсинга**: граф не трогаем (см. 4.3), текст пользователя в textarea **сохраняется как есть** (ничего не перезаписываем сериализатором), обновляется только статус-строка.
   - **Toggle «Скрыть/Показать»**: переписывает textarea только если тот «чист» (равен последней сериализации графа). Если в textarea неслитая правка или ошибка — toggle лишь переключает флаг `showComments`, а новое представление применится при следующем успешном merge.
4. Статус-строка: «Синхронизировано», «Ошибка D2: строка N — ...», «Новых блоков: 2 (авто-позиция)».
5. Сохранение в localStorage — как сейчас (`queueSave`), плюс `order` и `showComments`.

## 10. Поведение по сценариям (чек-лист)

| Сценарий | Ожидаемое поведение |
|---|---|
| Переименование на строке (аннотированный вид) | Позиция сохраняется (комментарий на строке) |
| Переименование в чистом виде | Позиция сохраняется через эвристику (label/соседи) или авто-позиция |
| Перенос строки элемента | Позиция сохраняется (id тот же) |
| Перенос + переименование | Best effort: эвристика; fallback авто-позиция |
| Вставка нового блока | Авто-позиция, порядок в конец |
| Удаление блока | Нода и рёбра удаляются; позиции остальных не меняются |
| Смена подписи ребра | Ребро обновляется, позиции не трогаются |
| Ошибка синтаксиса D2 | Граф не меняется, статус с номером строки; сырой текст в textarea не перезаписывается |
| Ключ с точкой в кавычках (`"b.c"`) | Разрешается как литерал; приоритет самого длинного ключа над путём |
| Ребро к необъявленному блоку (`a -> b`) | Неявная нода `b` создаётся с авто-позицией; явное объявление позже сливается по id |
| Переключение «Скрыть/Показать» | Меняется только текст, схема и граф не трогаются |
| Комментарий в конце строки элемента | Сохраняется инлайн (`trailingComment`), позиционный маркер дописывается после: `Client # note # @d2pos 60,300` |
| Строка-комментарий перед элементом | Сохраняется в `comments[]` и выводится той же строкой над элементом |
| Комментарий перед первым элементом / в конце файла | `headerComments` / `trailingComments` сохраняются на месте |
| Комментарий-«подделка» маркера (`# @d2pos 5,5`) | Распознаётся как позиционный (зарезервированный формат, редкий случай) |
| Перезагрузка | Восстанавливаются граф, порядок, вьюпорт и состояние кнопки |

## 11. Порядок работ (этапы)

1. **Модель и сериализаторы** (чистый + аннотированный). Критерий: round-trip тест на текущем демо-графе.
2. **Парсер** чистого и аннотированного D2 (с извлечением `@d2pos`, отделением `trailingComment` и построением `order`). Критерий: демо-код парсится в тот же граф.
3. **Merge-слой идентичности** (ключ → эвристики → авто-позиция). Критерий: сценарии из раздела 10.
4. **Авто-расстановка** новых блоков. Критерий: вставка в код → блок появляется на схеме без наложений.
5. **UI**: редактируемый textarea, кнопка «Скрыть/Показать», статус, debounce, сохранение `order`/`showComments`. Критерий: ручные сценарии из раздела 10.
6. **Упорядочение по стрелкам** (`sortByArrows`). Критерий: юнит-тесты порядка + визуальная проверка.
7. **Миграция v1 → v2** localStorage. Критерий: старые данные открываются с построенным `order`.

## 12. Тесты

- Юнит (извлечённый JS + node): парсер (квотинг, вложенность, пути, рёбра, цепочки, списки, `#` в строках, извлечение `@d2pos` + отделение `trailingComment`, строки-комментарии), сериализаторы-паритет, merge-сценарии, `sortByArrows` (в т.ч. циклы, ромбы, контейнеры), авто-расстановка без пересечений.
- E2E (puppeteer, как раньше): ввод в textarea → схема обновилась через ~1 c; ошибка D2 не ломает граф; toggle не трогает схему; перезагрузка восстанавливает всё; паритет clean/annotated через `d2` CLI.
- Round-trip: `graph → serializeAnnotated → parse → merge` ⇒ позиции и порядок сохраняются.

## 13. Ограничения v1 и будущие улучшения

**v1 поддерживает:** ключи, `label`, вложенность, рёбра (в т.ч. цепочки и списки), маркеры `@d2pos`, комментарии пользователя (строки и инлайн), `rawAttrs` (best effort).

**Не поддерживается (осознанно):** классы и `@`-директивы, импорты, переменные/функции/массивы, `style`-деревья как отдельная грамматика, `near`, HTML-метки, иконки shapes. При встрече — сохранить в `rawAttrs` либо пометить ошибкой с номером строки (не молча ронять).

**Зарезервированный формат:** маркер `# @d2pos x,y` — служебный. Пользовательский комментарий, заканчивающийся точно таким паттерном, будет распознан как позиционный и его «хвост» отброшен. Лечится заменой маркера на более редкий, если конфликты станут реальными.

**Известные конфликты (редкие, документированы):**
- ключ-литерал с точкой vs путь: существует и `"b.c"`, и `b` с ребёнком `c` — приоритет у самого длинного ключа (литерала), рёбра к `"b.c"` пишутся как `"b.c"` без дробления;
- размеры (`w/h`) не восстанавливаются из текста (в D2 их нет) — только через `rawAttrs`.

**Улучшения после v1:**
- редактирование на месте (d2oracle-подобное) для идеальной сохранности форматирования;
- полноценный инкрементальный layout (dagre с закреплением узлов);
- карта переименований `oldKey → newKey` для правок через диалог редактора;
- экспорт «D2 с раскладкой» для переноса в другие среды.
