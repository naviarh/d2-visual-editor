# План: Undo/Redo и хранение диаграмм в браузере

Статус: **черновик — на согласование**
Ветка: `main` (по согласованию — `feature/undo-browser-files`)
Дата: 2026-08-09

---

## 1. Цель

Две независимые возможности для визуального редактора:

1. **Undo/Redo** — отмена последнего действия и возврат отменённых действий. Глубина отмены — параметр, по умолчанию **100**, задаётся настройкой `undoLimit` в `localStorage["d2editor:ui:v1"]` (в будущем будет меняться со страницы настроек).
2. **Хранение диаграмм в браузере** — сохранение текущей диаграммы как именованного файла и открытие ранее сохранённого файла прямо на веб-странице. Используются оба механизма браузера: **IndexedDB** (база файлов) и **localStorage** (сессионное автосохранение, префы, имя текущего файла).

## 2. Принятые решения (по обсуждению)

| Вопрос | Решение |
|---|---|
| Параметр глубины undo | Настройка `undoLimit` в `d2editor:ui:v1`, default 100, читается при старте |
| Ctrl+Z при фокусе в textarea кода | Нативный откат текста (браузер); откат графа — кнопки и хоткеи вне текстового поля |
| Содержимое файла диаграммы | Граф целиком (payload как в автосохранении: позиции, порядок, вьюпорт, showComments) |
| Модель сохранения | Явное: «Сохранить в браузер» → имя файла → запись (перезапись только по подтверждению) |
| Хранение истории undo/redo | **Только изменения** (дельты между пре- и пост-состоянием); полный снапшот — транзиентно, в стек не попадает |

Не откатывается undo: pan/zoom, выделение, переключение «Скрыть/Показать позиции», открытие/сохранение файлов (это отдельные команды).

## 3. Часть 1. Undo/Redo

### 3.1 Модель истории — хранятся только изменения

Новый модуль **`js/d2-history.js`** (ES5 UMD, без DOM, чистая логика — как остальные `js/*`).

В стеке хранится **патч** — дельта между пре-состоянием (до действия) и пост-состоянием (после), а не полные диаграммы. Полный снапшот (`snapshotState()`) существует только транзиентно — на время вычисления дельты — и сразу отбрасывается.

```js
createHistory(limit)                  // → { limit, undoStack: [], redoStack: [] }
diffStates(prevState, nextState)      // → patch | null (null — изменений нет)
pushState(hist, patch)                // добавить патч; при превышении limit — shift
                                      // самого старого; очистить redoStack
undo(hist)                            // → patch | null (патч переносится в redoStack)
redo(hist)                            // → patch | null
canUndo(hist) / canRedo(hist)         // boolean
clearHistory(hist)
applyStatePatch(state, patch, dir)    // dir: "before" | "after"; мутирует state
```

Патч — дельта двух состояний v2-payload:

```js
{
  nodes: { "<id>": { before: <node|null>, after: <node|null> } },
  edges: { "<id>": { before: <edge|null>, after: <edge|null> } },
  order: { before: [...], after: [...] } | null,       // присутствует, если изменился
  idCounter: { before: n, after: n } | null,  // в diff не участвует (см. ниже)
  viewport: { before: {x,y,zoom}, after: {...} } | null,
  showComments: { before: bool, after: bool } | null
}
```

- `before: null` — элемента не было в пре-состоянии (добавлен этим действием); `after: null` — элемент удалён этим действием.
- `nodes`/`edges` — только реально изменившиеся элементы (по id; сравнение значений узла/ребра, остальные не копируются).
- **Сравнение значений — каноническое**: узлы/рёбра сравниваются по каноническому JSON (ключи отсортированы рекурсивно). Порядок ключей у нод, созданных визуально (`addBlock`), и у нод, построенных парсером (после текстового merge `mergeGraph` возвращает `parsed`-ноды с перенесёнными полями — `js/d2-merge.js`), различается; при наивном `JSON.stringify` одинаковое содержимое выглядело бы «изменённым» и каждая правка текста порождала бы патч со всеми нодами.
- **`idCounter` исключён из сравнения** (в патч не попадает): после текстового merge он детерминированно пересчитывается в `maxSuffix + 1`, не отражает намерений пользователя и расходится с UI-счётчиком (снимок-без правок создавал бы шумный шаг истории). После undo/redo будущие id просто продолжают нумерацию — коллизий нет, id уникальны по `Map`-поиску.
- `applyStatePatch(..., "before")` восстанавливает пре-состояние (undo), `"after"` — пост-состояние (redo).
- `undo(hist)`/`redo(hist)` не требуют текущего состояния: патч самодостаточен.

### 3.2 Снапшот (транзиентный), дельта и применение

В `index.html`:

- `const D2HIST = window.d2history;` + `const UNDO_LIMIT_DEFAULT = 100;`
- **`history = D2HIST.createHistory(undoLimitPref())`** — при старте читается `undoLimit` из `UI_KEY` (`Number.isFinite`, клампится в `[1, 1000]`), иначе `UNDO_LIMIT_DEFAULT`.
- `snapshotState()` → `structuredClone(currentGraph())` (фолбэк `JSON.parse(JSON.stringify(...))`). Клонируется **только пре-состояние**; в историю не попадает, отбрасывается сразу после вычисления дельты.
- `pushIfChanged(prev)` → `const patch = D2HIST.diffStates(prev, liveState()); if (patch) { D2HIST.pushState(history, patch); updateUndoUI(); }` — единая точка записи.
- `liveState()` → `currentGraph()` **без клонирования**: оба состояния (prev и live) проходят одну и ту же нормализацию `currentGraph()` (`{...n, children, x: n.x||0, y: n.y||0, hasPos:true, comments, trailingComment, rawAttrs}`). Это критично: без нормализации у живого узла нет `hasPos`/`comments`/`rawAttrs`/дефолтов `x`/`y`, и `diffStates` видел бы «изменения» на **каждой** ноде при **каждой** мутации. Полного клона пост-состояния нет: `diffStates` клонирует только изменившиеся элементы при формировании патча (иначе последующие мутации портили бы `before`/`after`).
- Паттерн мутации: в начале действия `const prev = snapshotState();`, после мутаций `pushIfChanged(prev);` (для drag — см. §3.3).
- `applyPatchToLive(patch, dir)`:
  1. `clearTimeout(textTimer)` — отменить несостоявшееся слияние текста.
  2. Собрать `st = { nodes, edges, order, idCounter, viewport, showComments }` (живые ссылки), `D2HIST.applyStatePatch(st, patch, dir)` (мутирует Map/массив на месте), синхронизировать обратно `order/idCounter/viewport/showComments` из `st`.
  3. Если в патче менялся `viewport` — `applyViewport(st.viewport)`.
  4. Сбросить транзиентное: `selectedId = null; selectedEdgeId = null; edgeSrc = null; groupParent = null;`.
  5. `render()` (diagram + queueSave/queueGen).
  6. `regenerateTextView()` — переписать textarea из восстановленного графа (явная команда, переписывание допустимо), `lastGraphText` обновится.
  7. `updateUndoUI()`.

`updateUndoUI()` ставит `disabled` на кнопках по `canUndo`/`canRedo`; вызывается из `render()` и после `pushIfChanged`.

**Стоимость (оптимизированный вариант):**

- **Запись** (фиксация действия): `snapshotState()` = построение `currentGraph()` O(N) + `structuredClone` O(N) (транзиентно) + повторный `currentGraph()` для `liveState()` O(N) + O(N) сравнений значений (канонический JSON — только для пар одного id). В стек уходит только O(изменённых) — для типового действия это 1 узел/ребро (+`order` при изменении).
- **Восстановление** (undo/redo): O(изменённых) — `applyStatePatch` меняет на месте только затронутые элементы (`Map.set/delete`, замена/вставка ребра в массиве, присваивание `order`/`viewport`/`showComments`). Рёбра, отсутствовавшие в текущем массиве, вставляются на стабильную позицию (по порядку id в восстановленном `order`), а не простым `push` — сохраняется порядок отрисовки. Единственная O(N)-операция — `regenerateTextView` (полная сериализация текста); она неизбежна для любой команды, меняющей граф, и нужна для синхронности textarea.
- **Память**: в стеке никогда нет полных диаграмм; `undoLimit` ограничивает число патчей.

**Применение отмены/повтора не пишет в историю** (запись живёт только в явных точках мутаций §3.3).

**Открытие файла из браузера (§4.5)** — не undo/redo: это полная замена состояния (`applyState(st)`: `applyGraph` + `applyViewport` + сброс транзиентного + `render` + `regenerateTextView`), после которой `clearHistory`.

### 3.3 Точки записи (таблица мутаций)

Единый паттерн: в начале действия `const prev = snapshotState();`, после завершения мутаций `pushIfChanged(prev);`.

| Действие | Функция | Где брать `prev` и вызывать `pushIfChanged` |
|---|---|---|
| Перетаскивание блока | `startDrag` / `onMove` / `onUp` | `prev` — один раз, в момент `moved` впервые становится true (до первого изменения `n.x/n.y`); `pushIfChanged(prev)` — в конце drag (onUp). Весь drag = 1 шаг |
| Новая стрелка | `handleNodeClick` (mode edge) | `prev` после `await openEditDialog(...)`, `pushIfChanged` после `edges.push` |
| Группировка/разгруппировка | `handleNodeClick` (mode group) | `prev` перед веткой `if (n.parentId === groupParent) … else if …`, `pushIfChanged` после неё |
| Переименование блока | `renameNode` | `prev` после `if (!name) return;`, `pushIfChanged` после мутаций |
| Подпись стрелки | `renameEdge` | `prev` после `if (label === ed.label) return;`, `pushIfChanged` после мутации |
| Удаление блока | `deleteNode` | `prev` после `if (!n) return;`, `pushIfChanged` после удаления (в т.ч. рёбер) |
| Удаление стрелки | `deleteEdge` | `prev` после проверки `i < 0`, `pushIfChanged` после удаления |
| Новый блок | `addBlock` | `prev` после `openEditDialog`, до `nodes.set`, `pushIfChanged` после |
| Смена формы | `shapeSel.onchange` | `prev` только если выбран «форм-овый» блок, до мутации `n.shape`, `pushIfChanged` после |
| Смена направления | `dirSel.onchange` | `prev` только если выбрано ребро, до мутации `ed.dir`, `pushIfChanged` после |
| Упорядочить по связям | `btnSort` handler | `prev` до `applyGraph(D2SORT.sortByArrows(...))`, `pushIfChanged` после |
| Правка текста | `onTextEdit` | `prev` после `if (!r.ok) return;` (снимок только при успешном парсе); `pushIfChanged(prev)` после `applyGraph(merged.graph)` |

**Правка текста:** дельта считается по фактическому результату merge — `diffStates` сам определяет, изменился ли граф. Пустая дельта (например, добавлен пробел) → `patch === null`, в историю не попадает. Сравнение значений узлов/рёбер покрывает: добавление/удаление/переименование, перенос строк, изменение координат в маркерах, правку комментариев.

### 3.4 UI и хоткеи

- В `.flowbar` панели «Схема», перед `+ Блок`, с разделителем:
  - `<button id="btnUndo" title="Отменить">↩</button>`
  - `<button id="btnRedo" title="Вернуть">↪</button>`
  - изначально `disabled`.
  - Символы кнопок — `↩` (отмена) и `↪` (возврат); при наведении курсора браузерный `title` показывает всплывающую подсказку «Отменить» / «Вернуть».
- `btnUndo.onclick = undoAction; btnRedo.onclick = redoAction;`
  - `undoAction()`: `const patch = D2HIST.undo(history); if (patch) applyPatchToLive(patch, "before");`
  - `redoAction()`: `const patch = D2HIST.redo(history); if (patch) applyPatchToLive(patch, "after");`
- Хоткеи в существующем `window.addEventListener("keydown", ...)` — **после** раннего выхода для `INPUT`/`TEXTAREA` (line ~1525), поэтому в textarea срабатывает нативный undo:
  - `(Ctrl|Meta)+Z` → undo; `Ctrl+Shift+Z` или `Ctrl+Y` → redo; `e.preventDefault()`.
  - Модалка не конфликтует: её `keydown` уже делает `stopPropagation()`.

### 3.5 Взаимодействие с пайплайном текста

- **Правка текста до слияния** (debounce 3 c ещё не истёк), пользователь жмёт «Отменить»: `applyPatchToLive` сбрасывает `textTimer` и переписывает textarea из восстановленного графа — незамереженный текст отбрасывается (это осознанная семантика явной команды).
- **Undo текстовой правки**: применяет дельту к живому графу и переписывает текст (`regenerateTextView`). Последующий ввод снова идёт через merge относительно восстановленного графа.
- **Ошибка D2 в textarea**: граф не менялся → `diffStates` вернул `null` → записи нет; «Отменить» восстановит предыдущее состояние и перепишет textarea (уберёт ошибочный текст).
- **Redo сбрасывается** при любой новой мутации (`pushState` очищает `redoStack`) — стандартная семантика.
- Историю не храним в localStorage (транзиентная).

### 3.6 Граничные случаи

- Стек переполнен: `pushState` вытесняет самое старое (`shift`).
- **Целостность патча**: `applyStatePatch` клонирует значения (`before`/`after`) при материализации в живой граф (JSON-clone). Последующие мутации (например, drag меняет `n.x/n.y` у живого узла) не портят сохранённые копии — повторный `redo` и повторный drag корректны.
- Удаление ноды, на которую указывает `edgeSrc`/`groupParent` — undo не требуется, но `applyPatchToLive` сбрасывает транзиентное.
- Быстрые повторные действия: каждая запись — один шаг; лимит применяется к стеку.
- Память: патч компактен (только изменившиеся узлы/рёбра + `order`/`idCounter` при изменении); для типового действия — 1 узел/ребро. Полные снапшоты живут только во время вычисления дельты.
- Нет истории: кнопки `disabled`, хоткеи no-op.
- Открытие файла/старт: `clearHistory` (новый контекст документа).

## 4. Часть 2. Файлы в браузере

### 4.1 Разделение хранилищ («что и как эффективно использовать»)

| Механизм | Что хранит | Почему |
|---|---|---|
| **IndexedDB** (база `d2editor`, store `files`) | Именованные файлы диаграмм | Много файлов, потенциально крупных; структурировано (записи с ключом-именем); асинхронно — не блокирует UI; не ограничено ~5MB localStorage. Проверено экспериментально: работает и персистентно на `file://` в системном Chrome (puppeteer, перезагрузка и вторая вкладка) |
| **localStorage** | Ключи `d2editor:v1` (сессионное автосохранение) и `d2editor:ui:v1` (префы) — **без изменений** | Малый объём, синхронно, мгновенно при старте; «последняя сессия» восстанавливается даже без открытия файла |
| **localStorage `d2editor:ui:v1.currentFile`** | Имя текущего (последнего открытого/сохранённого) файла | Тонкий преф, не требует IDB |

### 4.2 IndexedDB-схема

- Имя БД: `d2editor`, версия `1`, object store `files`, `keyPath: "name"`, `autoIncrement: false`.
- Запись: `{ name: string, v: 1, graph: <payload>, savedAt: number, size: number }`. Поле `size` — приблизительный размер `graph` в байтах (`JSON.stringify(graphPayload()).length`), считается при `filePut`; нужно для отображения занятого места (§4.10).
- Хелперы в `index.html` (IDB — браузерный API, в чистые модули не выносим; тонкая обвязка UI):
  - `dbFiles(): Promise<IDBDatabase>` — открытие/кэш подключения (одно на страницу). База создаётся лениво при первом открытии (`onupgradeneeded` создаёт store `files`). При неудаче открытия кэш сбрасывается — следующая операция попробует снова.
  - **Изоляция кэша**: кэш — одна JS-ссылка (промис) на подключение **только к базе `d2editor`**. Его сброс/пересоздание не затрагивают localStorage (`d2editor:v1`, `d2editor:ui:v1`), другие IndexedDB-базы, in-memory-граф и undo-историю. `deleteDatabase("d2editor")` — единственная деструктивная операция, запускается только пользователем («Пересоздать базу файлов»).
  - `filePut(name, graphPayload)` / `fileGet(name)` / `fileList(): Promise<Array<{name, savedAt, v, size}>>` (без `graph` — для списка) / `fileDelete(name)` / `fileReset(): Promise<void>` — `indexedDB.deleteDatabase("d2editor")` + сброс кэша соединения + повторное открытие (создаёт чистую базу).
  - Все обёрнуты в try/catch → статус-строка при ошибке (private mode, quota, blocked), без падения.
- При записи IndexedDB сам делает structured-clone графа — «живые» мутации не портят сохранённое.

### 4.3 Рефакторинг payload

Вынести из `saveState` строитель полезной нагрузки:

```js
function graphPayload() {
  return {
    v: 1,
    nodes: [...nodes.values()].map((n) => ({ ...n, children: n.children.slice() })),
    edges, idCounter, viewport, order, showComments
  };
}
```

`saveState()` использует `graphPayload()`; сохранение файла — тоже. Формат файла совместим с автосохранением → при открытии можно применять тот же `applyState`.

### 4.4 Сохранение («Сохранить в браузер»)

`data-act="save-browser"` в `#copy-menu` → `saveToBrowser()` — открывает **модальное окно сохранения** `#save-modal` (поверх общего каркаса `showModal`, см. §4.6):

1. В поле ввода `#saveName` автоматически вписывается имя диаграммы, если оно уже есть (`currentFile`), иначе — дефолт `diagram`.
2. Кнопки: **«Сохранить»** / **«Отмена»**; Enter в поле = «Сохранить», Escape = «Отмена» (закрывает окно, ничего не сохраняя).
3. «Сохранить» с пустым именем → инлайн-ошибка в окне «Введите имя диаграммы» (окно не закрывается).
4. «Сохранить», имя **не существует** → `filePut(name, graphPayload())` → `currentFile = name` → `saveUiPrefs({ currentFile: name })` → закрыть окно → статус «Сохранено в браузер: name».
5. «Сохранить», имя **уже существует** → окно **не закрывается**: внутри появляется подтверждение «Диаграмма с именем "name" уже существует.» с кнопками **«Заменить»** / **«Отмена»**.
   - **«Заменить»** → `filePut(name, ...)` (перезапись) → закрыть окно → статус «Сохранено в браузер: name».
   - **«Отмена»** → скрыть подтверждение, вернуться к редактированию имени (поле сохраняет введённое значение).
6. Ошибки IDB → инлайн-сообщение в окне, статус «Не удалось сохранить файл в браузере».

### 4.5 Открытие («Открыть из браузера»)

`data-act="open-browser"` → `openFileListModal()`:

1. `fileList()` (сортировка: `savedAt` по убыванию).
2. Показ модалки-списка: имя + дата + кнопки «Открыть» / «Удалить»; пустой список → «Нет сохранённых файлов».
3. **Открыть**: `fileGet(name)` — список `fileList()` приходит **без `graph`** (лёгкий) → валидация записи (`v:1`, массивы `nodes`/`edges`) → `applyState(record.graph)` → `D2HIST.clearHistory(history)` → `currentFile = name` → `saveUiPrefs({ currentFile: name })` → закрыть модалку → статус «Открыт: name». Автосохранение сессии перепишется через `queueSave` (перезагрузка восстановит открытый файл).

`applyState(g)` — единая замена состояния (общая для открытия файла и старта): `applyGraph(g)` (nodes/edges/order/idCounter), применить `g.viewport` (`viewport` + трансформация, если есть), `showComments = g.showComments`, сброс транзиентного (`selectedId`/`selectedEdgeId`/`edgeSrc`/`groupParent`), `render()`, `regenerateTextView()`, `updateUndoUI()`. После открытия файла — `clearHistory` (новый контекст документа).
4. **Удалить**: `confirmDialog('Удалить файл "name" из браузера?')` → `fileDelete(name)` → обновить список.
5. Битая запись → пропустить со статусом «Файл повреждён и пропущен».

### 4.6 Модалки — общий каркас `showModal`

Общий promise-подобный каркас (по образцу текущей `openEditDialog`, `index.html:915-948`), без фреймворков. Один раз реализует: показ/скрытие оверлея, клик по оверлею, Enter/Escape, очистку слушателей, resolve результата.

```js
const session = showModal({
  title: "…",
  showInput: { value: "…" } | null,     // null — поля ввода нет (подтверждения)
  buttons: [{ label, primary?, onClick }],
  onEnter: () => …,
  allowOverlayClose: true | false,
  allowEscapeClose: true | false
});
session.close(result);      // закрыть и разрешить `session.closed`
await session.closed;
```

- `session` — управляющий объект: `close(result)`, `setContent(el/HTML)`, `setButtons([...])`, `setTitle(...)` — позволяет менять содержимое и кнопки **без закрытия** (фазы внутри одного окна).
- Разметка — существующий `#modal-overlay`/`#modal-box`; содержимое `#modal-box` наполняется каркасом/модалкой динамически (существующий `#modal-input` остаётся дефолтным телом для `showInput`).

Надстройки над каркасом:

- **`openEditDialog({title, value})`** — тонкая обёртка: `showInput`, кнопки «Отмена»/«OK», Enter=OK → `string | null` (текущее поведение сохраняется).
- **`confirmDialog(message, { okLabel, cancelLabel }): Promise<"ok"|"cancel">`** — обёртка без поля ввода; Enter=ok, Escape=cancel. Используется для подтверждения **удаления** файла и предложения **«Пересоздать базу файлов»**.
- **`#save-modal`** — один `showModal` на всё окно: `showInput` (префилл `currentFile || "diagram"`), кнопки «Сохранить»/«Отмена». При «Сохранить» с существующим именем — **без закрытия**: `session.setContent` → «Диаграмма "name" уже существует.», `session.setButtons` → «Заменить»/«Отмена»; «Заменить» сохраняет и `session.close(true)`, «Отмена» возвращает фазу ввода (поле сохраняет значение). Пустое имя / ошибка IDB — инлайн-сообщение через `session.setContent`. Escape и клик по оверлею: в фазе ввода — `close(null)`; в фазе подтверждения — возврат к вводу (окно остаётся).
- **`#files-modal`** — `showModal` со списком через `session.setContent`: `fileList()` → строки (имя + дата + «Открыть»/«Удалить»); «Открыть» — `fileGet(name)` (список без `graph`) → валидация записи → `applyState(record.graph)` → `clearHistory` → `currentFile` → закрыть; «Удалить» — `confirmDialog` → `fileDelete` → перерисовать список; «Закрыть» — `session.close()`; пустой список → «Нет сохранённых файлов». Внизу списка — строка занятого места (§4.10).

### 4.7 Текущий файл

- `currentFile` читается из `UI_KEY` при старте (используется как префилл при сохранении).
- Показывается в UI: маленькая метка в `.outbar` панели «Код D2» (справа от split-button): «Файл: name» (скрыта, если файл не открыт). (Опционально — можно отложить; префилл работает и без неё.)

### 4.8 Ошибки и ограничения

- `file://`-среда: IDB подтверждён рабочим в системном Chrome (та же среда, что и E2E). Если в другом браузере IDB недоступен — команды показывают статус-ошибку, приложение продолжает работать (автосохранение localStorage нетронуто).
- Перезапись — только по явному подтверждению «Заменить» (инлайн в окне сохранения, окно не закрывается).
- Имена файлов — любые непустые строки после `.trim()` (это имена-ключи в IDB, не пути).

### 4.9 Поведение при отсутствии или повреждении базы

- **Базы ещё нет** — штатный первый запуск, специальной обработки не требуется: `dbFiles()` открывает `d2editor` (версия 1), `onupgradeneeded` создаёт store `files`, операция завершается успешно. «Открыть из браузера» показывает «Нет сохранённых файлов», «Сохранить в браузер» создаёт первую запись.
- **Повреждённая база / сбой открытия** (`indexedDB.open` → `onerror`/`onblocked`/`DOMException`): `dbFiles()` отклоняет промис, кэш соединения сбрасывается (следующая операция попробует открыть заново — ошибка может быть временной, например, при очистке хранилища). Команда (сохранение/открытие списка) показывает **модалку-сообщение** через `confirmDialog('База файлов браузера недоступна (повреждена или заблокирована).', { okLabel: "Пересоздать базу файлов" })`:
  - **«Пересоздать базу файлов»** → `fileReset()` (`deleteDatabase("d2editor")` + повторное открытие чистой базы) → при успехе повторно выполнить исходную команду (сохранение/открытие); при повторном сбое — снова показать модалку.
  - **«Отмена»** → закрыть модалку, ничего не делать. Схема, undo/redo и localStorage-автосохранение продолжают работать — IDB-функционал изолирован. Предупреждаем в модалке, что пересоздание удалит сохранённые файлы (текст сообщения: «…Недоступна… Пересоздание удалит сохранённые файлы.»).
- **Открытие успешно, но store отсутствует** (повреждённая схема): `transaction.objectStore("files")` бросает `NotFoundError` — ловится тем же try/catch, поведение как при сбое открытия (та же модалка с «Пересоздать базу файлов»).
- **`onblocked`** (другая вкладка держит старое соединение): команда показывает модалку «База файлов браузера занята другой вкладкой. Закройте другие вкладки и повторите.»; «Пересоздать» в этой ситуации бесполезно (deleteDatabase тоже заблокируется), поэтому кнопки «Отмена»/«OK» — только повтор. Тем не менее, для простоты допустим единую модалку с «Пересоздать базу файлов»/«Отмена» (после «Пересоздать» при блокировке deleteDatabase завершится ошибкой → снова модалка).

### 4.10 Отображение занятого места

В `#files-modal` (низ списка) — строка-подпись с итогом. Два независимых источника:

- **Лимит и занятое место origin**: `navigator.storage.estimate()` → `{quota, usage}` (байты, асинхронно). `quota` — сколько всего выделено под хранилище приложения (включая IDB, localStorage, кэш), `usage` — сколько занято; «свободно» = `quota − usage`. Поддержка на `file://` в Chrome подтверждается в E2E. Фолбэки: API недоступен / бросил / вернул `quota: null` (private mode, блокировка хранилища) → строка-лимит не показывается, остаётся только счётчик файлов.
- **Занято файлами**: сумма `size` по записям `fileList()` (§4.2). Поле приблизительное (длина JSON графа), достаточно для подсказки; точный размер structured-clone в IDB не требуется.

Формат строки: «Файлы: N, занято X» и «Занято X из Y» / «Свободно X» (единицы КБ/МБ с округлением; < 1 КБ — байты). Обновляется при открытии модалки (асинхронно, без блокировки).

## 6. Тесты

### Юнит — новый `test/history.test.mjs` (`js/d2-history.js` через `createRequire`)

- `diffStates`: добавление узла/ребра (`before: null`), удаление (`after: null`), изменение значения (label/x/y/…); изменение `order`/`idCounter`/`viewport`/`showComments`; **пустая дельта → `null`**; отсутствие изменений не создаёт запись.
- `applyStatePatch` по направлениям: `"before"` восстанавливает пре-состояние (добавленные удаляются, удалённые возвращаются, изменённые откатываются), `"after"` — пост-состояние; round-trip `before`→`after` даёт исходное.
- **Клонирование**: после `applyStatePatch` мутация живой ноды не влияет на повторный `applyStatePatch` (stored `before`/`after` не портятся).
- push/undo/redo порядок (LIFO/FIFO); undo переносит патч в redoStack, redo возвращает;
- новая `pushState` очищает `redoStack`;
- лимит: `createHistory(3)` → после 5 push остаётся 3 шага (самые старые вытеснены), `canUndo` корректен;
- `undo` на пустой истории → `null`; `canUndo`/`canRedo` флаги; `clearHistory`.
- Память: патч от одного переименования не содержит копий неизменённых узлов (assert по количеству ключей `patch.nodes`).

Юнит-дополнение к `js/d2-serialize.js`:
- `toStandardD2(graph, refText)` === `serializeClean(graph, { refText })`; не содержит `# --- @d2pos`; паритет с `d2` CLI (в существующем CLI-тесте).

### E2E — `test/ui-smoke.test.mjs` (или новый файл `test/ui-history-files.test.mjs`)

- **Очистка**: helper очищает localStorage **и** `indexedDB.deleteDatabase("d2editor")` перед каждым тестом (иначе файлы переживают тесты).
- **Undo/Redo по кнопкам**: `+ Блок` → блок на схеме и в коде → «Отменить» → блок пропал (схема+код) → «Повторить» → вернулся.
- **Undo drag**: drag блока → позиция изменилась → «Отменить» → позиция и текст восстановлены.
- **Undo delete**: выделить блок → Delete → «Отменить» → блок и рёбра вернулись.
- **Undo текстовой правки**: `setText` (новая нода) → `waitEdit` → граф изменился → «Отменить» → граф и textarea вернулись.
- **Хоткеи**: `Ctrl+Z` / `Ctrl+Shift+Z` вне textarea; в textarea `Ctrl+Z` — нативный (textarea не переписывается приложением немедленно).
- **Лимит**: записать `undoLimit: 2` в префы **до загрузки страницы** (`page.evaluateOnNewDocument` — преф читается при старте), сделать 3 действия → откатываются только 2 последних.
- **Файлы**: «Сохранить в браузер» (имя, префилл `currentFile`) → «Открыть из браузера» → файл в списке; изменить схему → открыть сохранённый файл → состояние восстановлено (позиции, текст); повторное сохранение того же имени → инлайн-подтверждение «Заменить»/«Отмена» **без закрытия окна сохранения** (после «Отмена» поле имени сохраняет значение; после «Заменить» — перезапись и закрытие); пустое имя → инлайн-ошибка; «Удалить» → файл исчез.
- **Персистентность**: перезагрузка страницы → файл всё ещё в списке.
- **Место для хранения**: после сохранения файла `#files-modal` показывает «Файлы: N, занято X» и «Занято X из Y» (непустые, корректно растущие значения после второго сохранения); fallback — при подмене `navigator.storage.estimate` на `() => Promise.reject()` строка-лимит скрыта, счётчик файлов остаётся.
- **Импорт из файла (D2)**: `page.$("#import-file")` + `uploadFile` с аннотированным `.dd2` (с `# --- @d2pos`) → содержимое textarea заменено, маркеры **сохранены**, блоки встали по позициям; то же с `.txt` (чистый D2) и `.d2` → работает; бинарный/битый файл → статус-ошибка, содержимое не изменилось.
- **Экспорт в файл / Экспорт в D2**: контент проверяется юнит-тестами (`serializeAnnotated` содержит маркеры, `toStandardD2` === `serializeClean`, паритет через `d2` CLI); сам скачивание — через существующую механику `exportD2` (в E2E не тестируется).
- **IDB недоступен (эмуляция повреждения)**: через `page.evaluateOnNewDocument` подменить `indexedDB.open` так, чтобы **первый** вызов завершался `onerror`, а последующие — реальным API → «Сохранить в браузер» показывает модалку «База файлов браузера недоступна (повреждена или заблокирована)» с кнопками «Пересоздать базу файлов»/«Отмена»; «Отмена» → модалка закрылась, схема и автосохранение работают; повторное сохранение → модалка снова; «Пересоздать базу файлов» → `fileReset()` → сохранение успешно («Сохранено в браузер: …»).
- Статусы: «Сохранено в браузер: …», «Открыт: …», «Ошибка D2…» не ломает историю.

## 8. Ограничения и будущие улучшения

- Undo не покрывает pan/zoom и выделение (осознанно).
- `undoLimit` сейчас только читается из префов; UI-настройки нет — появится на странице настроек (поле уже зарезервировано).
- Файлы в IDB привязаны к origin (на `file://` — к среде Chrome); между разными браузерами/профилями файлы не переносятся — для переноса остаются «Экспорт/Импорт D2» (файлы ОС).
- Возможное развитие: автовосстановление последнего открытого файла, переименование файла, поиск по имени, экспорт файла IDB в `.d2`.
- IDB-модалка и confirm — переиспользование существующих паттернов оверлеев; новых зависимостей нет.
