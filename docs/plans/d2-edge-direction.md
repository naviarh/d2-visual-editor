# План: направленность стрелок связей между блоками

Статус: **реализовано** — js-модули, UI, юнит-тесты (187/187) и E2E (19/19) зелёные, документация обновлена. Этап готов к код-ревью и коммиту.
Ветка: `feature/edge-direction`.
Эталон: страница `d2lang.com/tour/connections/` и установленный CLI `d2` v0.7.1 (`/home/i/.local/bin/d2`) — рендер и `d2 fmt` сверены с реальным выводом.

## 1. Цель и границы

**Цель.** Поддержать в редакторе четыре типа направленности стрелок D2 — `->` (прямое, по умолчанию), `<-` (обратное), `<->` (обе стороны), `--` (без стрелки) — как в текстовом редакторе (синтаксис идентичен D2, включая однострочные цепочки), так и в визуальном редакторе (выпадающий список направлений рядом с кнопкой «+ Стрелка»). Параллельные связи между одной парой блоков визуально разводятся, чтобы не сливались в одну линию.

**Вне скоупа.** Пометки/стили наконечников (`source-arrowhead`/`target-arrowhead`, формы наконечников, `style.filled` и т.п.), подписи у наконечников, `near`-позиционирование рёбер. Встреченные в тексте `source-arrowhead`/`target-arrowhead` продолжают храниться в `rawAttrs` lossless (как и сейчас, см. `RESERVED`).

**Критерий приёмки.**
- Четыре записи парсятся, рендерятся и сериализуются без потерь; `d2 fmt` принимает выводимый нами текст.
- Каждая запись в тексте — отдельная связь: `a -> b` + `a <- b` дают **два** ребра, `a -> b` дважды — **два** ребра (паритет с «repeated connections declare new ones»).
- Выбор стрелки на схеме и смена направления через список обновляет и схему, и текст; выбор направления без выделенной стрелки становится дефолтом для новых стрелок.
- Параллельные связи между одной парой отображаются разведёнными линиями (без совпадения траекторий).

## 2. Эталон: соединения в d2 v0.7.1 (сверено с CLI)

### 2.1 Четыре валидные формы связи

| Запись | Рендер (проверено на SVG) |
|---|---|
| `a -> b` | путь a→b, наконечник на конце (у b) — `marker-end` |
| `a <- b` | путь a→b, наконечник на источнике (у a) — `marker-start` |
| `a <-> b` | наконечники на обоих концах |
| `a -- b` | без наконечников |

- Текст сохраняет порядок как написан: `a <- b` рисует путь от `a` к `b`, стрелка «входит» в `a`. Семантически это связь b→a.
- d2 для наконечника в начале пути использует **отдельный зеркальный маркер** (`refX=3` против `refX=7` у end) с `orient="auto"` — остриё направлено в узел-источник. Наш end-маркер `refX=10`; для start нужен зеркальный треугольник с `refX=0`.
- `d2 fmt` сохраняет все четыре формы как есть (не нормализует `<-` в `->`).
- `-*` / `*-` — маркеры-формы наконечников, **не** направленность: парсятся как обычные рёбра, направление прямое (поведение уже было; сохраняем).

### 2.2 Слияние связей в d2 (важно для нашей модели)

Проверено CLI: **d2 объединяет** записи `a -> b` + `a <- b` в одну двунаправленную связь (1 путь с обоими наконечниками), потому что хранит соединения по паре узлов в текстовом порядке и OR-ит флаги наконечников. Аналогично сливаются эквивалентные формы одного направления: `a <- b` + `b -> a` → одна связь.

**Наше сознательное расхождение:** в редакторе каждая запись — отдельное ребро (`a -> b` + `a <- b` → два ребра, `a <- b` + `b -> a` → два ребра). Обе записи валидны для `d2` (и `d2 fmt` их оставляет), просто d2 сам их рендерит слитно. Это нужно, чтобы можно было явно указать две разнонаправленные (и две однонаправленные) стрелки между одной парой.

## 3. Модель данных (зафиксировано)

Ребро получает поле **`dir`** ∈ `{'->','<-','<->','--'}`; поле **не хранится** при `dir === '->'` (по умолчанию, обратная совместимость со старыми графами в `localStorage`). `source`/`target` хранятся **в текстовом порядке** (как набрано в D2) — без разворота `<-`.

- **Идентичность связи = точная запись** `(source, target, dir)`:
  - парсинг не дедуплицирует (каждая запись — новое ребро, id `eN`);
  - merge матчит по этой тройке (через трансляцию id при переименовании узлов);
  - `a <- b` и `b -> a` — разные ребра (разные тройки).
- **Семантические концы** (для layout/sort, где направление стрелки важно): для `dir === '<-'` семантический источник = `target`, цель = `source`; для остальных — как в тексте. Локальный хелпер `edgeEndpoints(ed)` в каждом нужном модуле (модули не импортируют друг друга).
- **Цепочки** (`A -> B <- C <-> D`): уже разбираются циклом в `parseEdge` (`sources = targets`); каждое звено несёт собственный `dir`.

## 5. UI

### 5.1 Список направлений `#dirSel`

`<select id="dirSel">` сразу справа от `#btnEdge` (после кнопки «+ Стрелка»). Всегда активен (не `disabled`). Название кнопки (показ по умолчанию) — **«Направление»**, обозначает прямое направление (дефолт). Пункты выпадающего списка:

| value | Пункт |
|---|---|
| `->` | Направление (дефолт) |
| `->` | Прямое |
| `<-` | Обратное |
| `<->` | Обе стороны |
| `--` | Без стрелки |

Два пункта разделяют `value="->"`: «Направление» — дефолтный показ кнопки, «Прямое» — явная подпись прямого направления.

### 5.2 Поведение

- **Выбрана стрелка** (`selectedEdgeId`): `renderHint()` синхронизирует `dirSel.value` с `ed.dir`; смена значения мутирует ребро (`ed.dir = value`; при `value === '->'` — удалить поле) → `render()` + `queueSave()` + `queueGen()` (текст переписывается через регенерацию).
- **Ничего не выбрано**: значение списка — дефолт для **новой** стрелки (не сбрасывается при кликах/рендере). В `handleNodeClick` (режим «Стрелка») новое ребро получает `dir: dirSel.value`.
- **Убран guard дубликатов** при создании стрелки (`edges.some(ed => ed.source===src && ed.target===n.id)`) — повторное создание пары добавляет ещё одно ребро (паритет с п.2.2).

### 5.3 Рендер стрелок

- В `#edges` добавляется `<marker id="arrow-start">` — зеркальный к `#arrow`. Финальная геометрия маркеров (уточнена в 5.4): `markerUnits="userSpaceOnUse"`, треугольник 24×12, остриё в начале координат, `refX = ∓6` (end `-6`, start `+6`) — остриё выступает на 6px за конец пути.
- Каждое ребро по `dir`:
  - `->`: `marker-end="url(#arrow)"`
  - `<-`: `marker-start="url(#arrow-start)"`
  - `<->`: оба маркера
  - `--`: ни одного
- Геометрия пути не меняется (путь всегда от `source` к `target` в текстовом порядке) — меняются только маркеры.

### 5.4 Параллельные связи (фан-аут)

Сейчас все связи одной пары рисуются по одному лучу «центр→центр» (`edgeGeometry`) — совпадают. Решение — параллельный сдвиг лучей:

1. В `renderEdges` сгруппировать рёбра по **неупорядоченной** паре `(source, target)` (иначе `A -> B` и `B -> A` — одно направление, но разный текст-порядок — попадали бы в разные группы и совпадали).
2. Для группы размера `count` индексу `i` назначить смещение `d = (i − (count−1)/2) · spacing`, `spacing = 21px` (для `count=1` → `d=0`, поведение не меняется). Знак `d` умножается на `±1` по текстовому порядку (`source < target`): нормаль в `edgeGeometry` считается от луча в текстовом порядке и зеркалится для обратной записи, поэтому без коррекции знака обе линии ложились бы на одну сторону.
3. `edgeGeometry` получает параметр смещения: единичная нормаль `n = (−ady, adx)/L` (перпендикуляр к лучу); начальная точка луча сдвигается на `d·n`; пересечение с контуром считается тем же `outlineIntersect` → точки анкера остаются **точно на контуре** любой формы.
4. **Остриё и граница**: маркеры переведены на `markerUnits="userSpaceOnUse"`, треугольник удлинён вдвое (24×12 вместо 12×12), остриё в начале координат; `refX = ∓6` — остриё выступает на 6px за конец пути. `edgeGeometry` обрезает путь на `EDGE_INSET = 6` вдоль оси подхода **только у конца с маркером** (для `->` — цель, для `<-` — источник, для `<->` — оба, для `--` — ни один, такой конец вплотную к границе), поэтому линия не доходит до границы там, где есть остриё, и остриё (выступающее ровно на 6px) стоит точно на границе и не портится толщиной линии.
5. То же применяется в экспорте `buildSVG` (консистентность интерактива и SVG-файла).
